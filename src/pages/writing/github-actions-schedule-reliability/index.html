GitHub Actions schedules ran hours late, and an hourly one rarely ran

Last updated 2026-11-12

Conclusion. Do not rely on the schedule event for anything that has to happen at a given time. In my repositories, two daily schedules ran every day for over three months, but always late: usually by two to four hours, and by up to more than nine. An hourly schedule in another repository ran only about once every six or seven hours. When a Cloudflare Worker called workflow_dispatch on a cron instead, a run started every hour at the minute it was asked for. Separately, two public repositories whose default branch had not changed for 83 days still had their schedules enabled, so an unchanged default branch alone does not trigger the 60-day rule.

Evidence

From the run records of the Actions REST API, measured 2026-11-12. "Late" means the time between the cron time and the moment GitHub created the run (created_at).

GitHub's documentation allows for all of this. It says a schedule event "can be delayed during periods of high loads", that "high load times include the start of every hour", and that "if the load is sufficiently high enough, some queued jobs may be dropped". Its advice is to schedule at another minute of the hour. Repo A runs at :10, and the hourly schedule never used minute :00 (it ran at :07, :37 and :25). Both were still late or mostly missing.

The daily jobs arrived late. The hourly one mostly did not arrive. A missing hour leaves nothing in the run list: no failed or cancelled run takes its place. I don't know why those runs disappeared instead of arriving late.

What I did instead: call workflow_dispatch from outside

An external scheduler can start a run with a POST to /repos/OWNER/REPO/actions/workflows/WORKFLOW/dispatches. Since 2026-02-19, setting "return_run_details": true in the request body makes the endpoint answer 200 with workflow_run_id, run_url and html_url. Without it, the answer is 204 with an empty body. With the ID, the caller can record which run it started.

  • Any scheduler with a reliable clock will work. I used a Cloudflare Worker with a Cron Trigger, so I don't have to run a server.
  • The token is a fine-grained personal access token for that one repository only, with Actions: Read and write and an expiry date. It is stored as a Worker secret, not in code.
  • I kept the schedule event as a fallback at a different minute. The job must therefore be safe to start twice. Mine uses a concurrency group and checks what has already been done.
  • To check that the Worker is still triggering runs, count only workflow_dispatch runs. If you also count the fallback schedule, a dead Worker goes unnoticed.

The 60-day rule

The documentation says: "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." In two of the public repositories above, the last commit on the default branch was on 2026-08-21. On 2026-11-12, 83 days later, their scheduled workflows were still active. Both workflows force-push their output to a separate output branch every day, and both repositories have Dependabot branches. So these repositories were not inactive. All this shows is that an unchanged default branch is not enough to disable a schedule. Which kind of activity counts is not documented, and I could not test it from here. Check the workflow's state through the API, and give every scheduled workflow a workflow_dispatch trigger so you can run it by hand.

Method

  • Runs: gh api --paginate "repos/OWNER/REPO/actions/workflows/FILE/runs?event=schedule&per_page=100", reading created_at. The same with event=workflow_dispatch for the Worker's runs.
  • Delay: each run's created_at minus the cron time it belongs to. Measured only for schedules that run once a day, where each run clearly belongs to one cron time. On the four-a-day schedule, delays of several hours make some runs impossible to match to a cron time, so only the count is given.
  • Hourly window: from the first to the last scheduled run (Nov 3 17:42 to Nov 12 01:36 UTC). The cron minute was changed twice during this window (:07, :37, then :25).
  • Workflow state: gh api repos/OWNER/REPO/actions/workflows, reading state. Last default-branch commit: gh api "repos/OWNER/REPO/commits?sha=main&per_page=1".
  • Sources: GitHub Docs, Events that trigger workflows: schedule. GitHub Changelog, 2026-02-19: Workflow dispatch API now returns run IDs.
